================================================================================

1.1 Account Registration & Login
    - Secure registration, login, password reset, and invite-based onboarding

      password-reset workflows

1.2 Role-Based Access Control (RBAC)
    Stored role strings (exact): Agent, TransactionCoordinator, TeamLead,
    Attorney, Admin, Client, ForSaleByOwner, Vendor.
    UI labels: Agent, Transaction Coordinator, Team Lead, Attorney, Admin,
    Client, For Sale By Owner, Vendor.
    "Elf" is the historical product nickname for Transaction Coordinator;
    one admin payments surface still shows "Elf (Transaction Coordinator)".
    Platform admin is NOT a role — it is users.is_platform_admin (boolean).
    Tenant owner is NOT a role — it is tenants.owner_user_id == users.id.

    Self-signup (public /register) is limited to: Agent, Team Lead,
    Transaction Coordinator, Admin. Attorney, Client, For Sale By Owner,
    and Vendor join by invitation (or platform provisioning).

    Roles:
      a) Agent
         - Create transactions, confirm wizard data, assign/modify tasks
         - Approve AI communications, upload/delete documents
         - Communicate with all parties, set payment information
         - Assign Transaction Coordinators to their profile
         - Owns personal playbook (checklists, notes, vendors, resources)
           unless on a team that inherits the team playbook
      b) Transaction Coordinator (Elf)
         - Same transaction-workspace rights as Agent on assigned deals
           (2026-04-24 policy: TC = Agent rights on transaction surfaces)
         - Manage assigned transactions, assign/complete tasks
         - Upload/delete documents, approve AI emails
         - Communicate with vendors and clients
         - If standalone, can set payment information
         - CANNOT change master task templates or override agent decisions
         - CAN create transactions (code: canCreateTransaction = true)
      c) Team Lead
         - Control team-wide task templates, modify dependencies/defaults
         - Oversee all team transactions, can act as agent
         - Assign/upload/delete documents, set payment information
         - Assign Transaction Coordinators to their team
         - Team Overview production dashboard + Teams management
      d) Attorney
         - New RBAC role that uses the same core transaction/document model as
           other internal users
         - Upload legal packets (title commitments, settlement statements,
           affidavits, signed amendments, recording packets)
         - Review title objections, settlement deltas, release timing, and
           recording/disbursement checkpoints for attorney-closing matters
         - Approve or hold attorney-owned sends/releases; every approval writes
           to communication history and audit logs
         - Can use AI-prepared packet indexing, comparisons, and request-note
           drafts
         - CANNOT delegate legal judgment, legal-equivalence decisions, or
           final packet release to AI
      e) Administrator
         - Manage users, set system-wide defaults
         - Configure AI behavior limits (set minimum confidence floor)
         - Access all data, set payment access (on/off)
         - Does NOT control/override team or agent task logic without system prompting
         - Execute communication log exports upon user request
      f) Client (Buyer/Seller in an Agent-Led Transaction)
         - View documents and milestones, ask questions/request info
         - Upload documents (cannot delete, but can flag for deletion)
         - CANNOT edit tasks, delete documents, or see internal notes
         - Can share milestones from their profile
         - Ability to turn on/off notifications
      g) For Sale By Owner / FSBO (stored: ForSaleByOwner)
         - Customer-facing, property-centric workspace for self-managed sales
           and listing prep
         - Upload/view/download documents, review milestones/messages, and ask
           for plain-English AI guidance
         - Can share read-only milestone links, manage notification
           preferences, and flag documents for deletion review
         - Can interact with assigned Velvet Elves support/guide contacts
         - CANNOT see internal workflow logic/notes, edit back-office tasks or
           approvals, or delete documents directly
      h) Vendor
         - Upload documents (if invited); can upload new iterations
           (old documents marked as legacy/outdated)
         - Receive documents, request information
         - Answer requests for task timeline adjustments
         - CANNOT view full document center, see tasks or timelines

2.1 Transaction Lifecycle

      Active Transactions expanded drawer):
      EM Delivered, Inspection Response, Appraisal Expected, CD Delivered,
      Cleared to Close, Closing Date (with time-of-day), Possession (with
      time-of-day)
    - Time-of-day stored separately for closing and possession dates
      (displayed as "Time: TBD" until set)
    - Populate vendor lists, state lists, agent lists
    - Intuitive forms with built-in validation
    - Support for 6 transaction types:
      1. Buyer - Financing
      2. Buyer - Cash
      3. Seller - Financing
      4. Seller - Cash
      5. Buyer & Seller - Financing (Both)
      6. Buyer & Seller - Cash (Both)
    - Use case must be confirmed before tasks are instantiated
    - For FSBO customers, support a property-centric pre-contract /
      listing-prep state before a file becomes an active transaction
    - FSBO property views should support prep milestones such as disclosures,
      photo approval, marketing/go-live target, and launch checklist

2.1a Transaction Statuses
    - Active: live transaction in progress
    - Incomplete: wizard started but not confirmed; saved as draft
    - Paused: agent manually pauses (task reminders stop; editing still
      allowed)
    - Completed: all tasks done + closing date passed
    - Closed: admin/agent marks as closed after post-closing review
    - Terminated: deal cancelled / fallen through (not a successful close)
    - Status transitions: Incomplete → Active (wizard confirmed);
      Active → Paused → Active (agent toggle);
      Active → Completed → Closed (manual or time-based);
      any live status → Terminated (deal cancelled; distinct from Closed)

2.2 Transaction Type Switching
    - If transaction type changes mid-process (e.g., Financing to Cash):
      targeted updates only (not full regeneration)
    - Check task IDs for completed status; do not regenerate completed tasks
    - Generate only new tasks that did not exist in previous use case
    - Log all updates for audit

2.3 Transaction Assignment

      notifications and additional task creation
    - Support reassignment and multiple participants per transaction

3. THE WIZARD (AI-DRIVEN TRANSACTION INTAKE ENGINE)
================================================================================

3.1 Wizard Philosophy
    - AI-driven: user uploads documents, AI extracts structured data,
      user confirms/edits, system builds transaction automatically
    - No mandatory manual form-filling upfront (document-first approach)
    - Manual entry fallback when AI extraction fails or documents unavailable
    - Manual entry fields: title company name, representative name, phone, email

3.2 Document Upload (Phase 1 — Upload)
    - Full-screen wizard at /transactions/new (no AppLayout chrome)
    - Drafts persist across devices via /api/v1/wizard-runs/current
    - Single upload interface for multiple files
    - Global drag-and-drop in the authenticated workspace hands files to this
      phase via IntakeConfirmationModal
    - Accepted formats: PDF, JPEG, GIF, DOC, DOCX, and other image types
    - File size limit: up to 20 MB per file
    - Order does not matter
    - Auto-compression for files over 10 MB (Pillow for images,
      Ghostscript for PDFs)
    - Multi-page document splitting: preview step for users to select page
      ranges and split into separate documents with names/metadata
    - Parse DOC/DOCX files (e.g., pre-approval letters) for loan officer
      contact info
    - Parsing is a TRANSIENT progress screen (not a stepper stop):
      Reading documents → Extracting property data → Identifying parties →
      Checking dates. OCR via Amazon Textract; extraction via the active
      AI provider. Back never returns to a finished parse.
    - After drop/upload, AI verifies what the document is, proposes a name,
      and (outside the wizard) asks which transaction it belongs to and
      whether it should be sent for signature

3.3 AI Document Parsing
    - Using switchable AI provider (OpenAI GPT or Claude — see 8.1a)
    - Extract from all uploaded documents:
      Property Data: street address, city, state, zip code
      Transaction Data: representation type, purchase price, financing type,
                        earnest money details, closing mode when applicable
      Timeline Data: contract acceptance date, inspection deadlines,
                     financing/appraisal deadlines, closing date,
                     date-based contingencies
      Party Data: buyer(s), seller(s), listing agent, buyer's agent,
                  loan officer, title company, closing attorney/settlement
                  attorney when present
    - Detect owner-occupied vs. investor/second home purchase (criteria:
      purchase agreement marking, down payment >= 20%)
    - Modify scripts accordingly for investor/second home focus
    - Per-field confidence chips and clickable citations (page + snippet)

3.4 Double-Check Mechanism for AI Parsing
    - Two-pass extraction system:
      Pass 1: Read document, produce interpretation
      Pass 2: Re-read using different prompt strategy/extraction template
    - Proceed only if both passes agree with high confidence on key fields
      (date, party, signature status, requested deliverable)
    - If disagreement: request clarification or route to human review
    - Handle edge cases: blurry docs, crooked scans, missing pages
      (halt and request better copy or route to human)
    - Autopilot: when ship-it confidence, double-check agreed, core fields
      complete, and no needs_review conflicts — compress review into the
      Verification hub

3.5 Contract Details (Phase 2)
    - Property address + price/dates/financing/contingencies/notes on one step
    - A "Found in the contract — needs your eyes" band surfaces no-default
      decisions: who orders title (required except attorney-controlled
      states), cash-deal appraisal election (required on every cash deal)
    - Address is AI-normalized; city/state/zip inconsistencies are flagged
    - User confirms/edits in place; no silent defaults for deadline windows
      (see §15)

3.6 Contacts & Fees (Phase 3)
    - Each party is a full contact card (name, email, phone, company)
    - Vendor-role contacts may defer email/phone to a "collect this" task
    - Professional + Transaction fee cards: paid by Buyer / Seller / Both;
      each paying side has its own amount and %/$ unit
    - Missing Info is a hidden auto-skip inside this phase when empty
    - If the user does not know a contact: AI public-source search, results
      labeled AI-sourced, confirmation required

3.7 Verification (Phase 4)
    - Review summary with source-linked value tables
    - Folded timeline anchors + AI proposal cards (deadlines, compliance,
      tasks), deal brief, signature decision, referenced-missing-doc requests
    - Create happens here via a full-width "Upload Transaction" button
    - Only after confirmation: create transaction, lock baseline dates,
      generate task list, auto-match compliance requirements
    - Optional "Suggest AI Improvement" for corrections to improve AI
    - Credit paywall when the workspace has no remaining prepaid deals

3.8 Retired wizard steps
    - Standalone Timeline, manual attach-documents Checklist, and Tasks
      preview are not navigable. They remain legal draft ids so stale
      wizard_runs coerce. Compliance editing lives on the deal workspace.

3.9 Signature Review in Wizard
    - Review documents for signatures
    - If unsigned document found and user has e-signature platform connected:
      offer to send for electronic signature upon transaction finalization
    - Track signature workflow: send, receive, replace original with executed
      copy (old goes to version history), distribute to identified parties
    - If no e-sign connected: inform user and suggest connecting

4. TASK ENGINE (MOST CRITICAL COMPONENT)
================================================================================

4.1 Task Philosophy
    - Use-case driven, dependency driven, mostly automated
    - Continuously optimized by AI
    - NOT static checklists

4.2 Task Templates (Master Library)
    - Import from legacy spreadsheet (50+ tasks from REWORKING TASK DB.xlsx)
    - Structure: Name, Description, Target (who), Dependencies (task or date),
      Float (days before/after), Automation level (Fully automated /
      AI-assisted / Manual), Use-case applicability (Buy-Fin, Buy-Cash,
      Sell-Fin, Sell-Cash)
    - Admin-configurable via UI: edit task definitions, add new tasks,
      configure dependencies
    - Task categories:
      Welcome & Communication: Buyer/Seller/Co-op Agent/Loan Officer Welcome,
                               New Transaction Added
      Documentation & Compliance: Review Documentation, Request/Deliver HOA Docs,
                                  Order/Confirm Title, Buyer Documentation,
                                  Deliver Title/Utility Info, Title Work Completed,

      Vendor & Contingency: Order/Confirm Home Warranty, Insurance Reminder,

4.3 Initial Task Generation
    - Upon wizard confirmation: tasks generated strictly from confirmed use case,
      confirmed dates, and dependency logic
    - No AI creativity at this stage

4.4 Dynamic Task Intelligence (AI Agent)
    - As transaction progresses:
      Detect completed steps automatically
      Recommend removal of unnecessary tasks
      Recommend adding missing tasks
      Detect document-based contingencies
      Suggest deadline adjustments (never auto-change)
      When a user creates a manual task, search for similar incomplete tasks
      and offer Add / Combine / Disregard options before saving
    - All additions/removals are RECOMMENDATIONS, not forced
    - Approval rules:
      Individual agents: approve for their transactions
      Team leads: approve for team-wide template changes
      Master task list additions: apply to all Active status transactions
    - Apply new dynamic tasks to: active, incomplete, paused transactions
    - Do NOT add retroactively to completed/closed transactions
    - Preview screen showing affected transactions before confirmation

4.5 Task Recommendation Transparency
    - Added tasks include: reason, source (document/pattern/behavior),
      suggested deadline
    - Removed tasks include: reason, option to restore
    - Nothing disappears silently: removed tasks "sleep"

4.6 Feedback Loop (Learning System)
    - After closing: prompt for quick feedback (useful/unnecessary/missing tasks)
    - AI adapts suggestions per agent or per team over time
    - Compliance tasks never fully removable from all transactions
    - Historical data per user for learning (no GDPR/CCPA compliance needed now)
    - Admin dashboard: track tasks added/removed globally for statistical analysis
    - Task completion rate metrics

4.7 Confidence Threshold System
    - Two-tiered system configurable per team:
      "Ship it" tier: confidence score >= 90% (auto-proceed)
      "I better see it first" tier: confidence score <= 75% (human review)
    - Admin sets global minimum confidence floor
    - Team leads configure higher thresholds but cannot go below admin minimum
    - Task-specific confidence thresholds:
      Lower risk: signature presence, field completion checks
      Higher risk: legal interpretation, clause meaning, obligations
    - UI validates in real-time with warnings; changes logged for audit

4.8 Notification & Reminders
    - Email reminders for due/critical tasks
    - Configurable reminder intervals (day before, due today, past due)
    - Push and in-app notifications
    - SMS reminders when that channel is enabled for the tenant/user
    - Compiled reminder summaries such as "You have 3 transactions with
      deadlines due tomorrow/today"
    - Daily summary email (only when tasks are due, not when there are none)

4.9 Task Sorting & Views

    - My Task Queue (/tasks/queue): personal task queue grouped by urgency

      (collapsed by default)
    - Sort options: Urgency (default), Due Date, Transaction, Status
    - Filter tabs: All | Overdue | Due Today | Upcoming | Completed
    - Per-task actions menu: Complete, Edit, Change Due Date (inline popover),
      Reassign (team members dropdown), View Transaction, Skip Task, Delete
    - Team Lead toggle: "My Tasks" / "Team Tasks" (team view shows all
      members' tasks with assignee column)
    - Sort tasks by vendor ("vendor carts"): follow up all tasks for one vendor
      in one email across multiple transactions
    - Highlight tasks with upcoming deadlines
    - Task Detail page (/tasks/:id): full task info, dependencies, activity
      timeline, parent transaction link, AI confidence/reason for
      AI-recommended tasks

4.10 AI-Generated Closing Checklists

15. TRANSACTION GENERATION SYSTEM - CLIENT-CONFIRMED REQUIREMENTS (Q&A 2026-07)
================================================================================

Source: Q&A_Transaction_Generation_System.md (Jake's answers to the five
open questions in TRANSACTION_SYSTEM_GUIDE.md Section 8, including the
Attorney/Title Workflow workbook he supplied for Question 5).
These are client decisions. Where anything below conflicts with an earlier
section of this document or with TRANSACTION_SYSTEM_GUIDE.md, this section
prevails. Implementation plan: TRANSACTION_GENERATION_SYSTEM_UPDATE_PLAN.md.

15.1 Title-Ordering Determination (Q&A Question 1)
    - Read who-orders-title from the contract whenever the contract states it
      (existing behavior, retained)
    - When the contract is silent (or the AI read is below the acceptance
      threshold), the user entering the transaction MUST be asked to answer
      "who orders title" on the wizard verification screen before the deal
      can be created; it becomes a required field with a mouse-only control
    - NO brokerage-level default for the silent case (explicitly rejected:
      a default could be incorrect and the user could overlook it)
    - Keep the "No title task was generated - confirm who orders title"
      coverage notice on the Tasks & create screen as the safety net
    - The confirmed answer must deterministically produce exactly one title
      task: "Order Title" (our side orders) or "Confirm Title Order" (the
      other side orders); the Buyer/Seller answer must be evaluated against
      the representation side to decide our-side vs counterparty

15.2 Contract Deadline Windows - No Standardization (Q&A Question 2)
    - NEVER pre-fill standard or brokerage-default deadline windows
      (inspection period, inspection-response window, HOA-document delivery
      window, insurance-commitment window); every number comes from the
      contract or from the agent
    - Confidence-banded extraction behavior, per field:
        >= 90%: value accepted automatically, shown with its citation
        70-89% (borderline): shown as an AI RECOMMENDATION that the agent
          must explicitly approve before it is used; never silently filled
        < 70% or not found: left blank for the agent to fill during
          submission (honest blank, with a short note)
    - Train/tune AI recognition of these four windows specifically; extract
      them as explicit day counts with per-field confidence and source
      citations, and measure recognition quality with the extraction
      benchmark so improvement is provable

15.3 Appraisal on Cash Deals (Q&A Question 3)
    - On EVERY cash deal, regardless of state, AI must review the contract
      for an explicit appraisal election (buyer elected vs waived appraisal)
    - Elected: appraisal tasks are generated
      Waived: no appraisal tasks
      Silent or unsure: NO appraisal tasks by default and the agent is
      PROMPTED to decide (client-confirmed: "Let's prompt the agent here.
      The better our inputs, the better our Agents can correctly work the
      file.")
    - The election read uses the same confidence-and-confirm machinery as
      15.2 (accept / recommend / blank+prompt)
    - Remove the current master-list behavior that attaches a cash appraisal
      follow-up task to every cash deal unconditionally
    - Provide a simple one-click control on the live deal to flip the
      appraisal answer later; flipping adds or removes the appraisal tasks
      with completed work preserved and the change audit-logged

15.4 Calendar Days vs Business Days (Q&A Question 4)
    - Default is ALWAYS calendar days, for every deadline
    - NO weekend/holiday roll of deadlines, in either direction: real estate
      timelines can end on holidays and weekends, so a computed deadline
      lands exactly where the count says. A timeline that hits too early is
      acceptable; one that hits late and misses a client deadline is not
    - AI reads each deadline's basis independently from the contract;
      business-day counting applies ONLY to a deadline the contract
      definitively writes in business days (or one an agent explicitly sets
      to business days)
    - Every deadline shows its basis in plain language (for example
      "5 business days after Date of Acceptance") with the contract citation
      when the basis was AI-determined
    - This supersedes the earlier roll-to-next-business-day convention
      described in TRANSACTION_SYSTEM_GUIDE.md Sections 4-7

15.5 All-50-States Support & Attorney Closing Workflows (Q&A Question 5)
    - The product is being built to sell to other brokerages, FSBO customers,
      and attorneys; it must be usable in all 50 states. Model this as two
      base workflows (title-company closing vs attorney closing) plus
      per-state differences, not fifty hand-built task lists
    - Build the attorney task lists by adapting the existing master lists
      for attorneys vs title companies, and ADD attorney-only steps that have
      no title-company equivalent (do not blindly swap)
    - NO single "attorney state" yes/no toggle. Use per-state workflow flags:
        requires_attorney_closing_control (true for NC, SC, GA, DE)
        requires_attorney_title_opinion_or_exam (true for NC, DE)
        requires_attorney_supervised_disbursement (true for SC, DE;
          conservative attorney-controlled for NC, GA)
        has_default_attorney_review_period (true only for the verified NJ
          scenario)
        attorney_review_trigger (delivery of signed contract / contract
          clause / none)
        title_company_role_allowed (support role in attorney-controlled
          states; mixed role in NJ/NY)
        agent_orders_title_default (false for NC, SC, GA, DE)
        fsbo_reassigns_agent_tasks_to_customer (true)
    - Verified state clusters (initial build):
        NC / SC / GA / DE: attorney owns the legal/title/closing workflow;
          the agent coordinates only. The agent's default task is "Confirm
          closing attorney selected and send executed contract", NOT "Order
          Title". No default attorney-review deadline unless the contract
          creates one. SC is modeled as attorney supervision across five
          components (title abstract, document preparation, closing,
          recording, disbursement), where supervision means the attorney
          reviewed the work product, not a checkbox
        NJ: attorney-review deadline of 3 BUSINESS days counted from
          DELIVERY of the completely signed contracts (not from acceptance),
          created ONLY when a real-estate licensee prepared the contract.
          Title company / title clerk / closing-agent roles remain in the
          workflow. Do not model NJ as attorney-only
        NY: attorney-approval deadline created ONLY when the contract
          contains the approval contingency, using the contract's stated
          period. Support both title pathways (attorney abstract/title
          opinion AND title company/title insurance). Do not force one NY
          workflow
        ALL OTHER STATES: standard title/settlement workflow. DO NOT
          classify a state as attorney-controlled until verified
    - Attorney-specific task library (added tasks, with default owners per
      Jake's workbook): confirm attorney selected; confirm attorney
      representation/scope ("confirm who represents whom"); send executed
      contract to attorney; attorney contract review (deadline only if
      state/contract creates one); order or supervise title search/abstract;
      preliminary title opinion or title certificate; review title results
      and exceptions; resolve title defects / curative work; apply for or
      coordinate title insurance; prepare or review deed; prepare or review
      mortgage/deed-of-trust documents; conduct or control closing;
      authorize or supervise disbursement; authorize or supervise recording;
      final title opinion / post-closing title work
    - FSBO / attorney-direct assignment rules: brokerage/agent coordination
      tasks are reassigned to the customer (or attorney), never left on an
      agent placeholder; attorney-required legal tasks always remain intact;
      NJ FSBO must NOT auto-create the 3-business-day review deadline when
      no licensee prepared the contract; NY attorney-direct may start with
      "attorney drafts/reviews contract before execution" rather than
      review-after-acceptance
    - Compliance guardrail (RESPA, 12 U.S.C. 2608): the seller cannot
      require the buyer to purchase title insurance from a particular title
      company; provider-selection UI must never hard-assign a provider
    - Jake's Attorney/Title Workflow workbook (embedded in
      Q&A_Transaction_Generation_System.md, with source citations) is the
      authoritative build matrix for clusters, flags, deadline logic, task
      library, and FSBO/attorney-direct rules

15.6 Cross-Cutting Delivery Constraints (re-affirmed for this workstream)
    - Every behavior above must be fully validatable through the frontend UI
      by non-developer real-estate professionals: mouse-first interactions,
      minimal typing, no dead ends in the end-to-end flow
    - Honest-blank principle: the system never invents dates, sides,
      elections, or workflows. It reads a value from the contract (with
      citation and confidence), recommends it for approval when borderline,
      or asks the user; it never guesses silently
    - Preview equals commit: what the wizard's review screens show is
      exactly what generation creates
    - The UI for these features must match the product's established design
      language and read as a modern professional tool for real estate
      experts
